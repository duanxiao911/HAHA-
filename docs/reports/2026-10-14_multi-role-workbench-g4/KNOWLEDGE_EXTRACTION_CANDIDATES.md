# G4 工程知识提炼候选

以下仅是候选，不自动写入全局知识树。

## KEC-01：多身份前端必须由服务端当前上下文驱动

- 结论：工作台接口不应接受 `role` 作为投影覆盖参数；服务端从持久化 `active_role` 读取并再次验证有效授权。
- 适用：多角色 SaaS、买卖双方平台、创作者/审核者后台。
- 证据：`?role=admin` 真实 E2E 请求返回当前服务端身份，未扩大权限。
- 边界：后台管理员代办/模拟功能需要独立、可审计的 impersonation（代操作）协议，不能复用普通角色参数。

## KEC-02：能力状态是业务契约，不只是 UI 禁用态

- 结论：用 `available | limited | blocked` 和明确原因表达真实成熟度，可避免静态页面把未接入能力冒充成功。
- 适用：分阶段平台、依赖外部 API 的 AI/交易功能。
- 证据：买家订单与 AI 学习在 API 和 UI 中均为明确阻断，不产生 Mock 指标。
- 反例：仅在按钮旁写“即将上线”，但 API 仍返回虚构订单或随机学习成绩。

## KEC-03：并行首屏请求要求初始化操作幂等且原子

- 结论：React/Next 首屏通常会并行拉取多个聚合接口；`SELECT -> INSERT` 默认初始化会在真实数据库中竞态。
- 方案：对唯一业务键使用数据库原生 `INSERT ... ON CONFLICT DO NOTHING/UPDATE`，再读取权威行。
- 证据：真实 PostgreSQL 首次加载先后暴露角色授权和用户设置唯一键冲突；原子化后全新账户 17 项 E2E 通过。
- 边界：原子 UPSERT 不能替代跨多个聚合根的事务设计。

## KEC-04：安全令牌轮换的附属审计也必须具备并发语义

- 结论：刷新令牌 CAS（比较并交换）成功后，审计写入若因锁冲突抛错，客户端仍会看到失败并产生语义混乱。
- 方案：保持令牌轮换一次性条件更新，并让同一 SQLite 测试适配器的轮换/审计写入串行且有限重试。
- 证据：修复前压力回归在审计写入处偶发锁错误；修复后连续 20 次通过。
- 边界：生产 PostgreSQL 应依赖事务和数据库锁语义，不照搬进程内锁。

## KEC-05：重大 UI 功能必须同时验证“真实来源”和“诚实空态”

- 结论：工作台验收不只看卡片是否出现，还要验证数据可创建、刷新恢复，以及未接入领域不会显示伪数据。
- 证据：创作者项目和学习资料在刷新后恢复；买家订单/售后保持阻断空态。
- 可复用测试模板：创建真实资源 -> 刷新页面 -> 重新读取投影 -> 验证服务端身份 -> 验证阻断能力 -> 检查浏览器异常。
